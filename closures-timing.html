Closures, composition & timing

Eleven small utilities that show up everywhere in JavaScript: toggles and samplers, memoize, currying, pipe and compose, chainable APIs, debounce, throttle and timer bookkeeping. Each has the core idea, a tested solution, the edge cases that break naive versions, and where to take it next.

They all rest on one fact: a function keeps access to the variables around it after the outer function has returned. Three patterns come out of that.

Private state

A counter, cache or timer ID lives in the outer function. The returned function reads and updates it on every call, and nothing outside can touch it.

Used in: toggle, sampler, once, memoize, debounce, throttle, clearAllTimeout

Collect until ready

Keep returning a new function that remembers the arguments so far. Act once you have enough, or when a stop signal arrives.

Used in: curry, infinite sum, placeholder curry, pipe and compose

Return the receiver

Every method returns the object it was called on, so calls chain. For async chains, record the steps first and run them later.

Used in: calculator, computeAmount, async person chain

Toggle, sampler and once

Seen in interviews atZeta (sampler)SDE2 problem set (toggle)Private state

Each returns a new function that carries a little private state: a position, a call count, or a "has it run" flag.

Approach

  1. toggle(...values): keep an index in the closure and advance it with modulo on each call.
  2. sampler(fn, n): count calls and only forward every nth one to fn.
  3. once(fn): a boolean flag plus the cached result. Later calls return the first result.
  4. Forward this and arguments with fn.apply(this, args) so the wrapper works as a method too.

Edge cases

  • Each call to toggle() must create independent state; two toggles should not share a position.
  • toggle() with no values would divide by zero in the modulo. Fail loudly instead.
  • once should drop its reference to fn after running so large closures can be collected.
  • If the first call to a once function throws, decide whether a retry is allowed (this version marks it done first, so it is not).

Go further

  • Add a reset() method to the sampler.
  • Write before(n, fn) and after(n, fn) from lodash using the same counter pattern.
  • Why does a closure-based counter survive between calls while a local variable in a normal function does not?
Show solution (try it yourself first) 
function toggle(...values) {
  if (values.length === 0) throw new TypeError('toggle needs at least one value');
  let i = -1;
  return () => {
    i = (i + 1) % values.length;
    return values[i];
  };
}

function sampler(fn, every) {
  let calls = 0;
  return function (...args) {
    if (++calls % every === 0) return fn.apply(this, args);
  };
}

function once(fn) {
  let done = false;
  let result;
  return function (...args) {
    if (!done) {
      done = true;
      result = fn.apply(this, args);
      fn = null; // let the original function be garbage collected
    }
    return result;
  };
}

Memoize with a key resolver and LRU limit

Seen in interviews atUber (part 2)SDE1 practice setPrivate state

Store results in a Map keyed by the arguments. The interesting decisions are how to build the key and when to evict.

Approach

  1. Build a key from the arguments. JSON.stringify(args) is a fine default for primitives.
  2. On a hit, return the cached value and move the key to the end of the Map so it counts as recently used.
  3. On a miss, call the function, store the result, and if the cache is over maxSize, delete the first key (the least recently used).
  4. Expose the cache on the function so callers can inspect or clear it.

Edge cases

  • JSON.stringify cannot tell undefined from missing, drops functions, and gives the same key for two different objects with the same contents. Allow a custom key function.
  • Object identity keys work with a Map (or a WeakMap for single-object arguments so entries can be garbage collected).
  • Caching a function that depends on this or on outside state gives stale answers.
  • Without a size limit, a memoized function called with many distinct inputs is a memory leak.

Go further

  • Add a time-to-live per entry.
  • Memoize async functions so that concurrent calls share one in-flight promise (see the async guide).
  • Compare with React.useMemo, which only remembers the last result.
Show solution (try it yourself first) 
function memoize(fn, { key = (...args) => JSON.stringify(args), maxSize = Infinity } = {}) {
  const cache = new Map();
  function memoized(...args) {
    const k = key(...args);
    if (cache.has(k)) {
      const value = cache.get(k);
      cache.delete(k); // move to the end: most recently used
      cache.set(k, value);
      return value;
    }
    const value = fn.apply(this, args);
    cache.set(k, value);
    if (cache.size > maxSize) cache.delete(cache.keys().next().value); // evict least recently used
    return value;
  }
  memoized.cache = cache;
  return memoized;
}

Curry a function with a fixed number of arguments

Seen in interviews atImpact AnalyticsSDE1 practice setCollect until ready

Keep collecting arguments across calls until there are as many as the function expects, then call it.

Approach

  1. Read the expected count from fn.length, but allow it to be passed in, because default and rest parameters are not counted.
  2. If enough arguments have arrived, call the original function.
  3. Otherwise return a function that merges the new arguments with the ones already collected and tries again.
  4. Because each step builds a new array, partial applications can be reused safely.

Edge cases

  • Accept several arguments per call: add(1)(2, 3) and add(1, 2)(3) should both work.
  • fn.length is 0 for (...args) => {}, so a rest-parameter function would be called immediately.
  • Do not mutate the collected array; const p = add(1) must stay usable after p(2)(3).

Go further

  • Curry with placeholders (two sections down).
  • Write uncurry or a partial-application helper like bind without this.
  • When is currying actually useful in UI code? (Building event handlers and selectors with fixed configuration.)
Show solution (try it yourself first) 
function curry(fn, arity = fn.length) {
  return function curried(...args) {
    if (args.length >= arity) return fn.apply(this, args);
    return (...more) => curried.apply(this, [...args, ...more]);
  };
}

Infinite curry: sum(1)(2)(3)()

Seen in interviews atZeptoMakeMyTripImpact AnalyticsSDE2 problem setsCollect until ready

There is no fixed length, so the caller has to say "done". Either an empty call ends it, or coercion to a number reads the total.

Approach

  1. Empty-call version: sum(a) returns a function. Given b, it returns sum(a + b); given nothing, it returns a.
  2. Coercion version: return a function with Symbol.toPrimitive set, so +sum(1)(2) or sum(1)(2) == 3 produces the total.
  3. The coercion version can accept several arguments per call by reducing them into the running total.

Edge cases

  • sum() with no arguments at all should return 0, not a function.
  • Passing 0 must not end the chain; check for undefined, not falsiness.
  • The coercion version is not a real number: typeof is still "function", and strict equality with 3 is false.

Go further

  • Make it generic: infiniteCurry(reducer, initial).
  • Support sum(1)(2).value() as an explicit terminator.
  • Explain how valueOf, toString and Symbol.toPrimitive interact during coercion.
Show solution (try it yourself first) 
// sum(1)(2)(3)() === 6
function sum(a) {
  if (a === undefined) return 0; // sum() on its own
  return function next(b) {
    if (b === undefined) return a;
    return sum(a + b);
  };
}

// sum(1)(2, 3)(4) == 10, read by coercion: +sumV(1)(2) === 3
function sumV(...args) {
  const total = args.reduce((s, x) => s + x, 0);
  const next = (...more) => sumV(total, ...more);
  next[Symbol.toPrimitive] = () => total;
  return next;
}

Curry with placeholders

Seen in interviews atTekion (Staff)Collect until ready

A placeholder reserves a slot to be filled later, so arguments can arrive out of order. The function runs only when the first n slots hold real values.

Approach

  1. Use a unique Symbol as the placeholder so no real argument can collide with it.
  2. The function is ready when there are at least arity arguments and none of the first arity is a placeholder.
  3. When more arguments arrive, fill placeholders from left to right first, then append the rest.
  4. Recurse with the merged list until it is ready.

Edge cases

  • join(_, _, 3)(1)(2) fills holes in order across several calls.
  • Placeholders beyond the arity should not block the call.
  • Use a fresh array on every step so partial applications stay reusable.

Go further

  • Let the placeholder be configurable, like lodash.curry.placeholder.
  • Support placeholders in partial and bind-style helpers too.
Show solution (try it yourself first) 
const _ = Symbol('placeholder');

function curryWithPlaceholder(fn, arity = fn.length) {
  return function curried(...args) {
    const ready = args.length >= arity && args.slice(0, arity).every((a) => a !== _);
    if (ready) return fn.apply(this, args);
    return (...more) => {
      // fill holes left to right, then append whatever is left over
      const merged = args.map((a) => (a === _ && more.length ? more.shift() : a));
      return curried.apply(this, [...merged, ...more]);
    };
  };
}

Pipe, compose, async pipe and pipe over an object

Seen in interviews atFlipkartRazorpayAbhibusAdobe (async compose)Collect until ready

Pipe passes a value through functions left to right; compose does the same right to left. Both are a single reduce.

Approach

  1. pipe(...fns) returns a function of the input that reduces over fns, feeding each result into the next function.
  2. compose is pipe with the list reversed. Copy before reversing so the caller's array is untouched.
  3. Async pipe: start from Promise.resolve(input) and chain .then(fn) for each function, so sync and async steps can mix.
  4. Object pipe: walk a nested object, call every function with the same arguments, and return an object with the same shape.

Edge cases

  • pipe() with no functions should return the input unchanged.
  • In the async version, a rejection anywhere skips the remaining steps and rejects the whole pipe.
  • In the object version, keep non-function values as they are, and handle arrays as well as plain objects.

Go further

  • Let each step see the original input as well as the previous result.
  • Add a tap or logging step that does not change the value.
  • How does this relate to middleware chains like Express or Redux? (Each middleware wraps the next.)
Show solution (try it yourself first) 
const pipe = (...fns) => (input) => fns.reduce((acc, fn) => fn(acc), input);
const compose = (...fns) => pipe(...[...fns].reverse());
const pipeAsync = (...fns) => (input) => fns.reduce((p, fn) => p.then(fn), Promise.resolve(input));

// Apply the same arguments to every function in a nested object, keeping its shape.
function pipeObject(obj) {
  return (...args) => {
    const out = Array.isArray(obj) ? [] : {};
    for (const [k, v] of Object.entries(obj)) {
      if (typeof v === 'function') out[k] = v(...args);
      else if (v !== null && typeof v === 'object') out[k] = pipeObject(v)(...args);
      else out[k] = v;
    }
    return out;
  };
}

Method chaining: calculator and computeAmount

Seen in interviews atNAVIBirdeyeReturn the receiver

Every method changes some state and returns the object again, so the next call can be written right after it. A final method reads the result.

Approach

  1. Class version: methods update this.total and return this.
  2. Closure version: keep the running total in a variable and return the same api object from every method.
  3. End the chain with an explicit reader such as value().

Edge cases

  • Arrow functions as methods break the class version, because their this is not the instance.
  • Validate inputs where they arrive: dividing by zero should throw at divide(0), not later.
  • Shared mutable state means two chains from the same instance affect each other. Return a new instance from each method if you need immutability.

Go further

  • Make it immutable: each method returns a new calculator.
  • Add undo() by storing a history of operations.
  • Where do you see this pattern in real libraries? (jQuery, query builders, test assertion libraries.)
Show solution (try it yourself first) 
class Calculator {
  constructor(value = 0) { this.total = value; }
  add(n) { this.total += n; return this; }
  subtract(n) { this.total -= n; return this; }
  multiply(n) { this.total *= n; return this; }
  divide(n) {
    if (n === 0) throw new RangeError('Division by zero');
    this.total /= n;
    return this;
  }
  value() { return this.total; }
}

// Same idea with a closure instead of a class
function computeAmount() {
  let total = 0;
  const api = {
    thousand(n) { total += n * 1e3; return api; },
    lacs(n) { total += n * 1e5; return api; },
    crore(n) { total += n * 1e7; return api; },
    value() { return total; },
  };
  return api;
}

Async method chaining with sleep and sleepFirst

Seen in interviews atCourse JS trackReturn the receiver

Chain methods only record steps in a queue. Execution starts on a later tick, after the whole chain has been written, and runs the queue in order.

Approach

  1. Keep an array of step functions. Synchronous steps log something; sleep(ms) adds a step that returns a timer promise.
  2. Every method pushes its step and returns the same object, so the chain keeps going.
  3. Start a runner with setTimeout(…, 0) so every chained call has registered first, then await each step in turn.
  4. sleepFirst(ms) uses unshift so its wait jumps ahead of everything already queued, including the greeting.

Edge cases

  • Starting the runner synchronously would execute steps before the rest of the chain is registered.
  • Use while (steps.length) await steps.shift()() so steps added while running are still picked up.
  • Several sleepFirst calls stack in reverse order, because each one is put at the very front.

Go further

  • Make the chain awaitable by adding a then method (a thenable).
  • Add a priority to every step instead of a single "first" escape hatch.
  • Add cancellation that clears pending timers.
Show solution (try it yourself first) 
// person('Asha').eat('idli').sleep(1000).eat('dosa').sleepFirst(500)
function person(name, log = console.log) {
  const steps = [() => log(`Hi, I am ${name}`)];
  const wait = (ms) => () => new Promise((resolve) => setTimeout(resolve, ms));
  const api = {
    eat(food) { steps.push(() => log(`${name} eats ${food}`)); return api; },
    sleep(ms) { steps.push(wait(ms)); return api; },
    sleepFirst(ms) { steps.unshift(wait(ms)); return api; }, // jumps the queue
  };
  // start after the synchronous chain has finished registering steps
  setTimeout(async () => {
    while (steps.length) await steps.shift()();
  }, 0);
  return api;
}

Debounce with leading, trailing, maxWait, cancel and flush

Seen in interviews atMoEngageArctic WolfTekionPayPayAbhibusHiver (as a hook)Private state

Wait until calls stop for wait ms, then run once with the latest arguments. Options decide whether the first call of a burst also runs, and whether a very long burst forces a call anyway.

Approach

  1. Every call stores its arguments and this, clears the timer and starts a new one. When the timer finally fires, the burst is over.
  2. leading: if no timer was running, this call starts a burst, so run it right away and clear the stored arguments.
  3. trailing: when the burst ends, run only if there are stored arguments, so a single leading call does not run twice.
  4. maxWait: a second timer started at the first call of a burst forces a run if the burst lasts that long.
  5. cancel clears both timers and the stored arguments; flush ends the burst immediately.

Edge cases

  • With leading and trailing both on, one isolated call must run exactly once. Use the lab with sparse clicks to see it.
  • Keep the latest arguments, not the first ones. The trailing call should see the final text in a search box.
  • Preserve this so it works as an object method or class field.
  • The return value of a debounced call is the result of the previous run, since the current one has not happened yet.

Go further

  • Write useDebounce and useDebouncedCallback hooks. Where should the timer live so re-renders do not reset it?
  • Return a promise that resolves with the eventual result.
  • Why is debounce plus a request ID still needed to avoid showing stale search results?
Show solution (try it yourself first) 
function debounce(fn, wait, { leading = false, trailing = true, maxWait } = {}) {
  let timer = null;     // fires when the burst goes quiet
  let maxTimer = null;  // forces a call during a long burst
  let pendingArgs = null;
  let pendingThis = null;
  let result;

  const invoke = () => {
    const args = pendingArgs;
    const ctx = pendingThis;
    pendingArgs = pendingThis = null;
    result = fn.apply(ctx, args);
  };
  const endBurst = () => {
    clearTimeout(maxTimer);
    timer = maxTimer = null;
    if (trailing && pendingArgs) invoke();
  };

  function debounced(...args) {
    const newBurst = timer === null;
    pendingArgs = args;
    pendingThis = this;
    if (newBurst && leading) invoke(); // the leading call uses up these arguments
    clearTimeout(timer);
    timer = setTimeout(endBurst, wait);
    if (maxWait !== undefined && maxTimer === null) {
      maxTimer = setTimeout(() => {
        maxTimer = null;
        if (pendingArgs) invoke();
      }, maxWait);
    }
    return result;
  }

  debounced.cancel = () => {
    clearTimeout(timer);
    clearTimeout(maxTimer);
    timer = maxTimer = null;
    pendingArgs = pendingThis = null;
  };
  debounced.flush = () => {
    if (timer !== null) {
      clearTimeout(timer);
      endBurst();
    }
    return result;
  };
  return debounced;
}

Throttle with leading and trailing options

Seen in interviews atGoogleTekionArctic WolfPrivate state

Run at most once per wait window. The leading call runs immediately; the latest call made during the window can run when it closes.

Approach

  1. If no window is open, run now (when leading) and open a window with a timer.
  2. Calls during the window only overwrite the stored arguments.
  3. When the window closes, run with the stored arguments if trailing is on, and open a new window for that call. Otherwise mark the throttle idle.
  4. With leading: false, the first call is stored and runs when the first window closes.

Edge cases

  • A trailing run must open a fresh window, or a call right after it would run too soon.
  • Turning off both leading and trailing means the function never runs. Reject that configuration or document it.
  • Throttle by timer drifts slightly under load. A timestamp check (Date.now() - last >= wait) is an alternative for the leading edge.

Go further

  • Throttle with requestAnimationFrame for scroll and resize work.
  • Throttle a queue of tasks so N run per second (a rate limiter).
  • When would you choose throttle over debounce? (Continuous feedback such as scroll position, versus a final value such as a search query.)
Show solution (try it yourself first) 
function throttle(fn, wait, { leading = true, trailing = true } = {}) {
  let timer = null;
  let pendingArgs = null;
  let pendingThis = null;
  let result;

  const cooldown = () => {
    timer = setTimeout(() => {
      if (trailing && pendingArgs) {
        result = fn.apply(pendingThis, pendingArgs);
        pendingArgs = pendingThis = null;
        cooldown(); // a trailing call opens a new window
      } else {
        timer = null;
      }
    }, wait);
  };

  function throttled(...args) {
    if (timer === null) {
      if (leading) result = fn.apply(this, args);
      else { pendingArgs = args; pendingThis = this; }
      cooldown();
    } else {
      pendingArgs = args; // keep only the latest call
      pendingThis = this;
    }
    return result;
  }

  throttled.cancel = () => {
    clearTimeout(timer);
    timer = null;
    pendingArgs = pendingThis = null;
  };
  return throttled;
}

clearAllTimeout

Seen in interviews atMetaFancodePrivate state

Wrap setTimeout and clearTimeout so every live timer ID is tracked in a Set. Clearing all is then a loop.

Approach

  1. Keep references to the original functions before replacing them.
  2. The new setTimeout wraps the callback so the ID removes itself from the Set when it fires, then records the ID.
  3. The new clearTimeout removes the ID from the Set and calls the original.
  4. clearAllTimeout clears every tracked ID and empties the Set. Return a function that restores the originals.

Edge cases

  • Remove IDs when timers fire, or the Set grows forever.
  • Pass extra arguments through: setTimeout(fn, ms, a, b) must still call fn(a, b).
  • In Node, timer IDs are objects rather than numbers. A Set handles both.
  • Patching globals affects every library on the page. Prefer a local timer manager in real code.

Go further

  • Do the same for setInterval.
  • Write a scoped version: createTimerScope() returning its own setTimeout and clearAll, without touching globals.
  • How do testing libraries fake timers? (They replace the same globals with a virtual clock, like the lab on this page.)
Show solution (try it yourself first) 
function trackTimeouts(target = globalThis) {
  const ids = new Set();
  const originalSet = target.setTimeout;
  const originalClear = target.clearTimeout;

  target.setTimeout = function (callback, ms, ...args) {
    const id = originalSet.call(target, (...a) => {
      ids.delete(id); // a timer that has fired no longer needs clearing
      callback(...a);
    }, ms, ...args);
    ids.add(id);
    return id;
  };
  target.clearTimeout = function (id) {
    ids.delete(id);
    return originalClear.call(target, id);
  };
  target.clearAllTimeout = () => {
    for (const id of ids) originalClear.call(target, id);
    ids.clear();
  };

  // undo the patch
  return () => {
    target.setTimeout = originalSet;
    target.clearTimeout = originalClear;
    delete target.clearAllTimeout;
  };
}
