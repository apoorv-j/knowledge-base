Async orchestration playbook

Eleven classic problems in coordinating asynchronous work in JavaScript: combining promises, limiting concurrency, queues, priorities, scheduling and dependency graphs. Each has the core idea, a tested solution, the edge cases that break naive versions, and where to take it next.

Almost every problem here is built from the same three moves. Once you can spot which ones a problem needs, the code mostly writes itself.

Counter + indexed slots

Write each result into results[i], decrement a counter, finish at zero. Keeps output order independent of finish order.

Used in: Promise.all, allSettled, any, mapLimit, dependency graph

Running count + pump

Track how many tasks are in flight. When one finishes, decrement and pull the next from a queue. This is how every concurrency limit works.

Used in: mapLimit, callback queue (Meta), async.queue (Uber), scheduler

Per-item state + head scan

Store pending / fulfilled / rejected per item, then walk from the front each time anything settles. Lets you answer "who wins by order" rather than "who finished first".

Used in: priority resolve, dependency graph, combinators with ordering rules

Timeline lab

Same six tasks, different orchestration. Drag durations, flip a task to fail, and watch when each strategy settles.

Promise.all, allSettled, race, any, finally

Seen in interviews atThoughtspotMakeMyTripArctic WolfAbhibusTekion SSE + StaffCounter + indexed slots

Each combinator is the same loop over the inputs. They only differ in what ends the loop early and what they collect.

Approach

  1. Convert the input with Array.from so any iterable works, and wrap every item in Promise.resolve so plain values work too.
  2. all: write into results[i], count down, resolve at zero; pass reject straight through so the first failure wins.
  3. allSettled: map every item to a promise that never rejects, then reuse all.
  4. race: attach the outer resolve and reject to every item. Whoever calls first wins; later calls are ignored by the promise itself.
  5. any: the mirror of all. Resolve on the first success, count failures, and reject with an AggregateError when they all fail.
  6. finally: run the callback on both paths, wait for whatever it returns, then pass the original value or error through untouched.

Edge cases

  • Empty input: all resolves with [], any rejects, race stays pending forever.
  • Results must be in input order, not finish order. Using push instead of results[i] is the most common bug.
  • Non-promise values in the array must still count toward completion.
  • finally should not change the resolved value, but an error thrown inside it does replace the result.

Go further

  • Why does calling resolve twice do nothing? (A promise settles once.)
  • Make Promise.all stop the remaining work on failure (pass an AbortSignal into each task).
  • Implement all with a concurrency limit. That is mapLimit, further down.
Show solution (try it yourself first) 
function promiseAll(items) {
  return new Promise((resolve, reject) => {
    const list = Array.from(items);
    const results = new Array(list.length);
    let remaining = list.length;
    if (remaining === 0) return resolve(results);
    list.forEach((item, i) => {
      Promise.resolve(item).then((value) => {
        results[i] = value;
        if (--remaining === 0) resolve(results);
      }, reject);
    });
  });
}

function promiseAllSettled(items) {
  return promiseAll(
    Array.from(items).map((item) =>
      Promise.resolve(item).then(
        (value) => ({ status: 'fulfilled', value }),
        (reason) => ({ status: 'rejected', reason })
      )
    )
  );
}

function promiseRace(items) {
  return new Promise((resolve, reject) => {
    for (const item of items) Promise.resolve(item).then(resolve, reject);
  });
}

function promiseAny(items) {
  return new Promise((resolve, reject) => {
    const list = Array.from(items);
    const errors = new Array(list.length);
    let remaining = list.length;
    if (remaining === 0) return reject(new AggregateError([], 'All promises were rejected'));
    list.forEach((item, i) => {
      Promise.resolve(item).then(resolve, (err) => {
        errors[i] = err;
        if (--remaining === 0) reject(new AggregateError(errors, 'All promises were rejected'));
      });
    });
  });
}

function promiseFinally(promise, onFinally) {
  return promise.then(
    (value) => Promise.resolve(onFinally()).then(() => value),
    (reason) => Promise.resolve(onFinally()).then(() => { throw reason; })
  );
}

Run promises in series, and sum results in parallel vs in sequence

Seen in interviews atPhonePeIntuitSDE2 practice setRunning count + pump

Series means each task starts only after the previous one finishes. Parallel means you start them all, then wait.

Approach

  1. Series: a for…of loop with await inside. Each iteration waits, so tasks never overlap.
  2. Parallel: call every function first to start the work, then await Promise.all on the promises.
  3. The classic trap is array.forEach(async fn): it fires everything in parallel and returns before any of it finishes.
  4. For "sum the results", run either version and reduce the returned array. The timing difference is the point: series takes the sum of durations, parallel takes the max.

Edge cases

  • Pass functions, not promises. A promise has already started by the time you have it, so it cannot be run "in series".
  • Decide what a failure means: stop the chain (shown here) or record it and continue.
  • Synchronous functions in the list must work too; await handles plain values.

Go further

  • Write series with reduce instead of a loop (p.then(() => fn()) chaining).
  • Callback-style version without promises: a recursive next(i) that calls itself from the callback.
  • What if you need the first N results as soon as they are ready? (Collect in a pool, emit in order.)
Show solution (try it yourself first) 
async function runInSeries(fns) {
  const results = [];
  for (const fn of fns) results.push(await fn());
  return results;
}

Retry a promise N times

Seen in interviews atGoogleImpact AnalyticsRunning count + pump

Wrap the attempt in a function you can call again, and decide after each failure whether to try again and how long to wait.

Approach

  1. Take a function, not a promise, because each retry needs a fresh call.
  2. On failure, check the attempt count and an optional shouldRetry(err). If either says stop, reject with the last error.
  3. Otherwise schedule the next attempt with setTimeout, multiplying the delay by a factor for exponential backoff.
  4. Wrapping the call in Promise.resolve().then(fn) turns a synchronous throw into a rejection, so it is retried too.

Edge cases

  • retries: 3 means 4 attempts in total. Pick one meaning and document it; off-by-one here is common.
  • Reject with the last error, not a generic message, so the caller can debug.
  • Do not retry errors that will never succeed, like a 400 or 401. That is what shouldRetry is for.

Go further

  • Add jitter (a random amount on each delay) so many clients do not retry at the same instant.
  • Make it cancellable with an AbortSignal.
  • Combine with a timeout per attempt (next section).
Show solution (try it yourself first) 
function retry(fn, { retries = 3, delay = 100, factor = 2, shouldRetry = () => true } = {}) {
  return new Promise((resolve, reject) => {
    const attempt = (n, wait) => {
      Promise.resolve()
        .then(fn)
        .then(resolve, (err) => {
          if (n >= retries || !shouldRetry(err)) return reject(err);
          setTimeout(() => attempt(n + 1, wait * factor), wait);
        });
    };
    attempt(0, delay);
  });
}

Fetch with a timeout

Seen in interviews atCourse JS trackCounter + indexed slots

Race the real work against a timer, and actually cancel the work when the timer wins.

Approach

  1. Create an AbortController and hand its signal to the task (for fetch, pass it in the options).
  2. Start a timer that aborts the controller and rejects with a clear message.
  3. Promise.race the task against the timer.
  4. Clear the timer in finally so a fast success does not leave a timer running.

Edge cases

  • Without the abort, the request keeps running in the background after the timeout fires, wasting bandwidth and possibly applying a stale response.
  • Always clear the timer; a leaked timer can keep a Node process alive.
  • Make the timeout error distinguishable from a network error so callers can retry only timeouts.

Go further

  • How would you support an outside cancel signal as well as the timeout? (AbortSignal.any, or forward one controller into the other.)
  • Add a timeout to every task in mapLimit.
Show solution (try it yourself first) 
function withTimeout(fn, ms) {
  const controller = new AbortController();
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => {
      controller.abort();
      reject(new Error(`Timed out after ${ms}ms`));
    }, ms);
  });
  return Promise.race([fn(controller.signal), timeout]).finally(() => clearTimeout(timer));
}

mapLimit: run async work with a concurrency limit

Seen in interviews atUberSDE3 / Staff practice setRunning count + pump

Start up to N tasks. Each time one finishes, store its result at its index and start the next. That is a pool, and it never leaves a slot idle.

A common solution splits the input into fixed batches and waits for each batch to finish. That works, but one slow task holds up its whole batch. The pool version shown here keeps every slot busy.

Approach

  1. Keep next (index of the next input to start), done (how many finished) and a results array.
  2. launch() takes the next index, calls the iteratee, and in the callback stores the result and calls launch() again.
  3. Kick things off by calling launch() min(limit, n) times.
  4. Resolve when done === n. On the first error, set a flag, reject, and stop launching.

Edge cases

  • Empty input must resolve immediately with [], otherwise the promise hangs.
  • Results stay in input order even though they finish out of order.
  • Ignore callbacks that arrive after a failure, and guard against an iteratee calling back twice.
  • A limit bigger than the input length should just run everything.

Go further

  • Why is the pool better than splitting into batches? Try both in the timeline lab above.
  • Return results as an async iterator as they complete.
  • Support promise-returning iteratees as well as callbacks.
Show solution (try it yourself first) 
function mapLimit(inputs, limit, iteratee) {
  return new Promise((resolve, reject) => {
    const results = new Array(inputs.length);
    let next = 0, done = 0, failed = false;
    if (inputs.length === 0) return resolve(results);
    const launch = () => {
      if (failed || next >= inputs.length) return;
      const i = next++;
      iteratee(inputs[i], (err, value) => {
        if (failed) return;
        if (err) { failed = true; return reject(err); }
        results[i] = value;
        if (++done === inputs.length) return resolve(results);
        launch();
      });
    };
    for (let k = 0; k < Math.min(limit, inputs.length); k++) launch();
  });
}

Engine that processes async callbacks

Seen in interviews atMetaFancodeRunning count + pump

At most two callbacks run at once. Extra ones wait in a queue of up to six, and the queue is drained FIFO by default or LIFO if the constructor says so.

Approach

  1. State: the order flag, a queue array, and a running count.
  2. process(cb): if fewer than two are running, run it now; otherwise push it onto the queue, unless the queue already holds six.
  3. When a callback finishes, decrement running and take the next one: shift() for FIFO, pop() for LIFO.
  4. Use finally so a callback that throws still frees its slot.

Edge cases

  • A rejected callback must not block the queue forever.
  • Some versions of this problem add a contradictory rule about switching to FIFO beyond three queued items. When a spec conflicts with itself, settle the intended behaviour before coding rather than guessing.
  • Overflow callbacks are dropped silently. Mention that in a real system you would report them.

Go further

  • Make the concurrency limit and queue size configurable.
  • Add a way to know when everything is finished (that is the Uber version next).
Show solution (try it yourself first) 
class QueueCallbacks {
  constructor(order = '') {
    this.lifo = order === 'LIFO';
    this.queue = [];
    this.running = 0;
    this.limit = 2;
    this.maxQueue = 6;
  }
  process(cb) {
    if (this.running < this.limit) return this.#run(cb);
    if (this.queue.length >= this.maxQueue) return; // discard overflow
    this.queue.push(cb);
  }
  #run(cb) {
    this.running++;
    Promise.resolve()
      .then(cb)
      .catch(() => {})
      .finally(() => {
        this.running--;
        if (this.queue.length) this.#run(this.lifo ? this.queue.pop() : this.queue.shift());
      });
  }
}

Async callback queue with push, unshift, drain and error

Seen in interviews atUber (twice)Tekion SSEFlipkartSDE3 / Staff practice setRunning count + pump

The same pump as mapLimit, but the queue stays open: tasks can be added at either end at any time, and listeners fire on errors and when the queue empties.

Approach

  1. Keep a tasks array, a running count and the two listener callbacks.
  2. push adds to the back, unshift to the front; both accept a single task or an array, then schedule a pump.
  3. pump() starts tasks while running < concurrency and tasks remain.
  4. In each task callback: decrement, report errors, call onComplete, then either fire drain (nothing running, nothing queued) or pump again.

Edge cases

  • Pumping in a microtask means a push followed by an unshift in the same tick respects the unshift.
  • Guard against a processor calling its callback twice, which would corrupt the running count.
  • drain should fire once per time the queue empties, not once per task.

Go further

  • Add pause() and resume().
  • Promisify it so await q.push(task) resolves with that task's result.
  • Add priorities (use a heap instead of an array).
Show solution (try it yourself first) 
function Queue(processorFn, onCompleteFn, concurrency = 1) {
  const tasks = [];
  let running = 0;
  let drainCb = () => {};
  let errorCb = () => {};
  const toArray = (t) => (Array.isArray(t) ? t : [t]);

  const pump = () => {
    while (running < concurrency && tasks.length) {
      const task = tasks.shift();
      running++;
      let called = false;
      processorFn(task, (data, error) => {
        if (called) return; // guard against double callbacks
        called = true;
        running--;
        if (error) errorCb(error, task);
        onCompleteFn(data, error, task);
        if (running === 0 && tasks.length === 0) drainCb();
        else pump();
      });
    }
  };

  return {
    push(t) { tasks.push(...toArray(t)); queueMicrotask(pump); },
    unshift(t) { tasks.unshift(...toArray(t)); queueMicrotask(pump); },
    drain(cb) { drainCb = cb; },
    error(cb) { errorCb = cb; },
  };
}

Resolve with the highest-priority success

Seen in interviews atPhonePeCourse JS trackPer-item state + head scan

Run everything in parallel, but only resolve when the highest-priority task that has not failed has succeeded.

Approach

  1. Sort by priority (lower number first) or use array order, then store a state per item: pending, fulfilled or rejected.
  2. Keep a head pointer to the best candidate still standing.
  3. Whenever anything settles, skip over rejected items at the head. If the head is fulfilled, resolve with it; if it is still pending, wait.
  4. If the head runs off the end, every task failed: reject.

Edge cases

  • A fast success at low priority must wait while a higher-priority task is still pending. The lab shows this.
  • Do not mutate the caller's array when sorting.
  • Empty input should reject immediately rather than hang.

Go further

  • How is this different from Promise.any? (Order of priority versus order of finishing.)
  • Sequential variant: try tasks one at a time and stop at the first success. Cheaper on resources, slower in wall time.
Show solution (try it yourself first) 
function priorityResolve(promises) {
  return new Promise((resolve, reject) => {
    const n = promises.length;
    const state = new Array(n).fill('pending');
    const values = new Array(n);
    let head = 0;
    if (n === 0) return reject(new Error('All promises failed'));
    const check = () => {
      while (head < n && state[head] === 'rejected') head++;
      if (head === n) return reject(new Error('All promises failed'));
      if (state[head] === 'fulfilled') resolve(values[head]);
    };
    promises.forEach((p, i) => {
      Promise.resolve(p).then(
        (v) => { state[i] = 'fulfilled'; values[i] = v; check(); },
        () => { state[i] = 'rejected'; check(); }
      );
    });
  });
}
// explicit priorities (lower number = higher priority)
function resolveWithPriority(items) {
  const sorted = [...items].sort((a, b) => a.priority - b.priority);
  return priorityResolve(sorted.map((x) => x.promise));
}

Promise scheduler that can be paused and resumed

Seen in interviews atHiveRunning count + pump

Run functions one at a time from an index. Pausing sets a flag the loop checks between functions; you cannot stop a function that is already running, only wait for it.

Approach

  1. State: the function list, the next index, a status and the promise currently running.
  2. run() loops from the stored index, awaiting each function and advancing the index, and checks the status before each step.
  3. pause() sets status to pausing and awaits the current function, so it resolves only once the run has actually stopped.
  4. getState() reports the status, the index in progress and the indices not yet run. Resuming is just calling run() again.

Edge cases

  • Calling run() twice must not start two loops. Guard on the status.
  • A function that throws should be reported but should not kill the loop.
  • Sync functions in the list must work too. Wrapping with Promise.resolve().then(fn) covers both.

Go further

  • Support cancelling the in-flight function (pass an AbortSignal to each function).
  • Allow N to run at a time while still being pausable. Combine this with the pump pattern.
Show solution (try it yourself first) 
class PausableScheduler {
  constructor(fns, { onCompleted = () => {}, onPaused = () => {}, onError = () => {} } = {}) {
    this.fns = fns;
    this.index = 0;
    this.status = 'idle';
    this.current = null;
    this.hooks = { onCompleted, onPaused, onError };
  }
  async run() {
    if (this.status === 'running') return;
    this.status = 'running';
    while (this.index < this.fns.length) {
      if (this.status === 'pausing') { this.status = 'paused'; this.hooks.onPaused(this.getState()); return; }
      const i = this.index;
      this.current = Promise.resolve().then(() => this.fns[i]());
      try { await this.current; } catch (e) { this.hooks.onError(e, i); }
      this.index++;
    }
    this.status = 'completed';
    this.hooks.onCompleted();
  }
  async pause() {
    if (this.status !== 'running') return;
    this.status = 'pausing';
    await this.current?.catch(() => {}); // the in-flight function cannot be interrupted, only waited on
  }
  getState() {
    return {
      status: this.status,
      inProgress: this.status === 'running' ? this.index : null,
      unexecuted: this.fns.map((_, i) => i).slice(this.index + (this.status === 'running' ? 1 : 0)),
    };
  }
  runAllUnexecutedFunctions() { return this.run(); }
}

Run async tasks with dependencies, like a build graph

Seen in interviews atUberPer-item state + head scan

Each task waits for its dependencies, then runs. Memoise the promise per task so a shared dependency runs exactly once, and independent tasks run in parallel automatically.

Approach

  1. Validate first: walk the graph depth-first to catch cycles and references to tasks that do not exist.
  2. start(name) returns a cached promise if one exists; otherwise it awaits Promise.all of its dependencies' start(), then runs the task.
  3. Call start for every task and wait with allSettled so one failure does not hide the others.
  4. Return the results and errors per task, plus a success flag.

Edge cases

  • A failed dependency means its dependents never run, and they should not appear in results.
  • Without the cache, a task that two others depend on runs twice.
  • A cycle would deadlock silently, so detect it before running anything.

Go further

  • Add a concurrency limit across the whole graph (feed ready tasks into a pool).
  • Return a topological order, or a level-by-level plan, without running anything.
  • Let a dependent run with partial results when an optional dependency fails.
Show solution (try it yourself first) 
async function runTasks(tasks, deps = {}) {
  const names = Object.keys(tasks);
  // cycle and unknown-dependency check
  const visiting = new Set(), visited = new Set();
  const visit = (n, path) => {
    if (!(n in tasks)) throw new Error(`Unknown task "${n}"`);
    if (visiting.has(n)) throw new Error(`Cycle: ${[...path, n].join(' -> ')}`);
    if (visited.has(n)) return;
    visiting.add(n);
    (deps[n] || []).forEach((d) => visit(d, [...path, n]));
    visiting.delete(n); visited.add(n);
  };
  names.forEach((n) => visit(n, []));

  const memo = new Map();
  const results = {}, errors = {};
  const start = (name) => {
    if (!memo.has(name)) {
      memo.set(name, (async () => {
        await Promise.all((deps[name] || []).map(start));
        try { return (results[name] = await tasks[name]()); }
        catch (e) { errors[name] = e; throw e; }
      })());
    }
    return memo.get(name);
  };
  await Promise.allSettled(names.map(start));
  return { success: Object.keys(errors).length === 0, results, errors };
}

Memoise callback-based async functions

Seen in interviews atRipplingUber L5a (SDE3)Counter + indexed slots

Cache finished results, and also remember calls that are still in flight so identical concurrent calls share one request instead of starting their own.

Approach

  1. The last argument is the callback; build the cache key from the rest (configurable for objects).
  2. Cache hit that has not expired: answer asynchronously with queueMicrotask, and move the key to the end for LRU order.
  3. Already in flight: add the callback to that key's waiting list and return.
  4. Otherwise call the real function. When it finishes, cache successes with an expiry, evict the oldest key past maxSize, and call every waiting callback.

Edge cases

  • Never cache errors, or one network blip poisons the key until it expires.
  • Always call back asynchronously, even on a cache hit. Mixing sync and async callbacks causes ordering bugs (often called "releasing Zalgo").
  • A Map keeps insertion order, which makes LRU eviction a delete-and-reinsert.

Go further

  • Add abort support, and a "latest wins" mode that cancels older calls for the same key.
  • Return stale data while revalidating in the background (stale-while-revalidate).
  • How does React Query or SWR solve the same problem?
Show solution (try it yourself first) 
function memoizeCallback(fn, { ttl = Infinity, maxSize = 100, key = (...a) => JSON.stringify(a) } = {}) {
  const cache = new Map(); // key -> { value, expires }
  const inflight = new Map(); // key -> [callbacks]
  return function (...args) {
    const cb = args.pop();
    const k = key(...args);
    const hit = cache.get(k);
    if (hit && hit.expires > Date.now()) {
      cache.delete(k); cache.set(k, hit); // refresh LRU position
      return queueMicrotask(() => cb(null, hit.value));
    }
    if (inflight.has(k)) return inflight.get(k).push(cb);
    inflight.set(k, [cb]);
    fn.call(this, ...args, (err, value) => {
      const waiters = inflight.get(k);
      inflight.delete(k);
      if (!err) {
        cache.set(k, { value, expires: Date.now() + ttl });
        if (cache.size > maxSize) cache.delete(cache.keys().next().value);
      }
      waiters.forEach((w) => w(err, value));
    });
  };
}
